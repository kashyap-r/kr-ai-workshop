
Instead of "requirements.txt, Why pyproject.toml?

pyproject.toml is the central project configuration, eventually it will contain 
    project metadata
    dependencies
    optional dependencies
    build configuration
    pytest
    ruff
    mypy
    coverage

This is a much cleaner production-orineted setup 

------------------------========================------------------------

Why each section exists

1. [build-system]
This tells Python tooling: "This project is a Python package and here's how to build/install it." We're using a standard package layout:
python/
├── src/
│   └── rag_platform/
└── tests/

2. [project]
This is the actual project metadata:
[project]
name = "rag-platform"
version = "0.1.0"
requires-python = ">=3.12"

dependencies = []
The idea is that the first implementation should have zero rutime dependencies 

3. [project.optional-dependencies]
This is Development dependencies, contains tools we need to develop and test the project.
They're not part of our RAG runtime

Runtime
   │
   └── dependencies = []

Development
   │
   ├── pytest
   ├── ruff
   ├── mypy
   └── coverage

Note: This distinction becomes useful later when our production container shouldn't contain unnecessary development tooling.

4. Why we're pinning ranges
For example: "pytest>=8.0,<9.0"
We don't want an arbitrary future major version silently changing behavior.
But we're also not hard-pinning: pytest==8.3.3 in the project definition. 
uv.lock will take care of the exact resolved versions.

pyproject.toml
        │ declares acceptable versions
        ▼
     uv sync
        ▼
    uv.lock
        │ exact resolution
        ▼
 reproducible environment

5. [project.scripts]

[project.scripts]
rag-platform = "rag_platform.main:main"
means that after installation we can eventually run: uv run rag-platform
instead of paython src/rag_platform/main.py

6. Pytest - the settings here tells pytest where our tests live. 

7. Ruff - We're using Ruff for:
    linting
    +
    import sorting
    +
    basic correctness rules

8. Mypy - This is especially important for our project.
We have:
strict = true (in .toml) because we're going to create lots of domain contracts.

For example, eventually: 
class DocumentLoader(Protocol):
    def load(
        self,
        source: DocumentSource,
    ) -> ParsedDocument:
        ...

I want the type checker to tell us if we accidentally implement:
def load(self, source: str) -> dict:
instead.
The type system becomes part of our architectural guardrail.
