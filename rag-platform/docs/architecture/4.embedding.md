# M4 — Embeddings & Vector Retrieval

## 1. Purpose

This module introduces semantic vector representations into the RAG pipeline.

The objective is to transform the chunks produced by the chunking stage into numerical vector representations that
can be compared against an embedded user query.

The resulting retrieval flow will eventually be:

Documents
    ↓
Parsing / Normalization
    ↓
Chunking
    ↓
Embedding
    ↓
Vector Store
    ↓
Similarity Search
    ↓
Top-K Relevant Chunks


This design deliberately separates experimentation from platform implementation.

The embedding model, similarity strategy, and vector store will first be evaluated independently and then 
the selected choices will be integrated into the platform.

---
# 2. What is an Embedding?
An embedding is a numerical representation of an object, in our case text.

A text chunk such as "Employees are entitled to 20 days of annual leave."
is transformed into a vector [0.021, -0.184, 0.731, ...]

The individual dimensions generally do not have directly interpretable meanings. The useful property is the 
relationship between vectors. Texts with similar semantic meaning should, ideally, occupy nearby regions of 
the embedding space.

For example: "How many annual leave days are employees entitled to?"
and
"Employees receive 20 days of annual leave each year."

should produce vectors that are more similar to each other than to an unrelated statement such as:
"Employees may work remotely two days per week."
The embedding therefore provides a representation suitable for semantic comparison.

---
# 3. Why Does RAG Need Embeddings?
Traditional keyword search primarily relies on lexical overlap.

Consider the query: "How many vacation days can I take?" and a document containing: "Employees are entitled to 
20 days of annual leave." 

The query contains "vacation" while the document contains "annual leave". A keyword-based system may struggle 
because the exact terms differ.
An embedding model can represent both texts in a semantic space where their meanings may be close.
This enables semantic retrieval:

User Query
    ↓
Query Embedding
    ↓
Compare with Document/Chunk Embeddings
    ↓
Rank by Similarity
    ↓
Retrieve Top-K
Embeddings therefore provide the semantic representation required for dense retrieval.

---
# 4. Dense Vector Representation
Embedding models generally produce dense vectors.
For example, a model might produce: [-0.14, 0.27, 0.03, ..., 0.61]
with hundreds or thousands of dimensions. Most dimensions contain non-zero values.

This differs from sparse representations such as traditional bag-of-words or TF-IDF vectors, where most 
dimensions are zero.

Dense representations are useful because neural embedding models can encode semantic relationships that are 
difficult to capture using simple lexical representations.

---
# 5. Query Embeddings vs Document Embeddings
There are two primary types of text entering our retrieval system:

### Documents / Chunks
During indexing:

Chunk
  ↓
Embedding Model
  ↓
Chunk Vector
  ↓
Vector Store

### User Query
During retrieval:

User Query
  ↓
Same Embedding Model
  ↓
Query Vector
  ↓
Vector Store Search

The query and indexed chunks must be represented in a compatible vector space. Therefore, the embedding 
model used for querying must be compatible with the model used when indexing the documents.

A change in embedding model generally requires re-embedding the indexed corpus.

---

# 6. Embedding Dimensions
An embedding model produces vectors with a fixed dimensionality.

For example:
Model A → 384 dimensions
Model B → 768 dimensions
Model C → 1536 dimensions

Higher dimensionality does not automatically mean better retrieval quality.

Increasing dimensionality can affect:
    * memory consumption
    * storage requirements
    * indexing cost
    * search cost
    * network transfer
    * infrastructure requirements

The appropriate dimensionality is therefore an empirical model-selection decision rather than something to 
maximize blindly.

---
# 7. Similarity and Distance
Once text has been converted into vectors, we need a way to determine how similar two vectors are.

Common approaches include:
    * Cosine similarity
    * Dot product
    * Euclidean distance

## 7.1 Cosine Similarity
Cosine similarity measures the angle between two vectors.
cos(A, B) = (A · B) / (||A|| ||B||)
For normalized vectors, cosine similarity is closely related to the dot product.

The important intuition is:
same direction       → high similarity
different direction  → low similarity
opposite direction   → low / negative similarity
Cosine similarity is widely used for semantic text retrieval.

---
## 7.2 Dot Product
Dot product is: A · B
For normalized vectors, ranking by dot product is equivalent to ranking by cosine similarity.
However, when vectors are not normalized, vector magnitude affects the result.
Whether this is desirable depends on the embedding model and retrieval design.

---
## 7.3 Euclidean Distance
Euclidean distance measures the straight-line distance between two points:
d(A,B) = sqrt(sum((Ai - Bi)^2))
Smaller distance means greater similarity.

For normalized vectors, Euclidean distance and cosine similarity produce equivalent rankings.
The exact relationship depends on the normalization assumptions.

---
# 8. Normalization
Vector normalization converts a vector to unit length.
For vector `A`:
A_normalized = A / ||A||

Normalization is important because it removes vector magnitude as a factor in similarity calculations.
This makes cosine similarity equivalent to the dot product for normalized vectors.
Whether normalization should be performed explicitly will be validated experimentally rather than assumed.

---
# 9. Embedding Model Selection
Selecting an embedding model is an architectural decision.
The model should not be chosen purely because it is popular or because it achieves a high benchmark score.

For our RAG system we need to consider:

### Retrieval quality
Does the model retrieve semantically relevant HR documents and chunks?

### Dimensionality
How large are the resulting vectors?

### Model size
How much memory/storage does the model require?

### Inference latency
How quickly can queries and documents be embedded?

### Throughput
How efficiently can the model process batches of chunks?

### Hardware requirements
Can it run locally on our development environment?

### Domain suitability
Does it perform well for our HR/employee-oriented corpus?

### Language support
Does it support the languages that our system is expected to handle?

### Licensing
Can the model be used under an appropriate open-source or permissive license?

### Operational complexity
How difficult is it to deploy and maintain?

The final choice will therefore be validated experimentally before incorporating into the design.

---
# 10. Local vs Hosted Embeddings

There are two broad architectural approaches.

## Local Embedding Model
Application
    ↓
Local Embedding Model
    ↓
Vector

Advantages:
    * no external API dependency
    * no per-request API cost
    * data can remain local
    * predictable availability
    * useful for development and experimentation
    * potentially lower latency after model loading

Trade-offs:
    * local compute requirements
    * model memory usage
    * operational responsibility
    * model download/storage
    * potentially lower quality than some hosted models

## Hosted Embedding API
Application
    ↓
Embedding API
    ↓
Vector

Advantages:
    * no local model management
    * potentially strong model quality
    * infrastructure managed by provider

Trade-offs:
    * API cost 
    * network latency
    * provider dependency
    * rate limits
    * availability dependency
    * data leaving the local environment
    * vendor-specific integration

For this project, we will initially evaluate **local open-source embedding models**.

---

# 11. Batch Embedding
Document indexing normally involves many chunks. Embedding each chunk individually can introduce unnecessary 
overhead.

Instead:
Chunk 1
Chunk 2
Chunk 3
...
Chunk N
     ↓
Batch
     ↓
Embedding Model
     ↓
Vector 1
Vector 2
Vector 3
...
Vector N

Batching can improve throughput because model inference can process multiple inputs together.
The optimal batch size depends on:
    * model
    * CPU/GPU
    * available memory
    * sequence length
    * desired latency

This will be considered during experimentation.

---
# 12. Embedding and Chunking Are Coupled
Embedding quality cannot be evaluated independently of chunking. The embedding model receives the chunk as its 
input. Therefore:

Chunking Strategy
        ↓
Text Presented to Embedding Model
        ↓
Embedding Quality
        ↓
Retrieval Quality

Poor chunking can produce poor embeddings even when the embedding model itself is strong.
For example, a chunk containing multiple unrelated sections may produce a vector representing a mixture of concepts.
Conversely, extremely small chunks may lose important contextual information.
Therefore, experimentation will use the chunks produced earlier rather than evaluating embeddings on isolated 
sentences only.

---
# 13. Similarity Search and Top-K
After embedding the query, the retrieval system compares the query vector with stored chunk vectors.
Conceptually:
Query Vector
      │
      ├──── compare ──── Chunk Vector 1
      ├──── compare ──── Chunk Vector 2
      ├──── compare ──── Chunk Vector 3
      ├──── compare ──── ...
      └──── compare ──── Chunk Vector N
                         │
                         ▼
                     Ranking
                         │
                         ▼
                       Top-K
`K` determines how many candidate chunks are returned.
For example: Top-K = 5 returns the five highest-ranked chunks.

A larger K increases recall but can introduce irrelevant context into the downstream LLM prompt.
A smaller K reduces context but risks missing relevant information.
The appropriate K is therefore a retrieval-quality and downstream-generation trade-off.

---
# 14. Vector Store Responsibilities
A vector store is responsible for storing and retrieving vector representations efficiently.
At minimum, our platform needs to support:
    Insert / Upsert
    Search
    Metadata
    Persistence

Conceptually:

Chunk
 ├── chunk_id
 ├── text
 ├── metadata
 └── embedding
          ↓
     Vector Store
The vector store should allow:
Query Embedding
      ↓
Similarity Search
      ↓
Top-K Results

The vector store is therefore an infrastructure component around vector indexing and retrieval.
It is not the embedding model itself.

---
# 15. Metadata
Embeddings alone are insufficient for a production RAG system.
Each vector should remain associated with metadata such as:
    document_id
    chunk_id
    source
    document_type
    page / section if available

This allows the retrieval layer to return not just: [0.12, -0.34, ...]
but something useful to the application:
{
    "chunk_id": "...",
    "text": "...",
    "metadata": {...},
    "score": 0.87
}
Metadata will also become important when we later introduce filtering.

---
# 16. Embedding Versioning
Embeddings are derived artifacts.
If the embedding model changes:

Model v1
   ↓
Vectors v1

cannot generally be mixed blindly with:
Model v2
   ↓
Vectors v2

because the vector spaces may differ.

Therefore, the platform should eventually be able to identify the embedding configuration used to create an index.
Relevant metadata includes:
    embedding_model
    embedding_model_version
    embedding_dimension
    normalization_strategy

Changing these characteristics may require rebuilding the vector index.

---
# 17. Architectural Boundary
The platform should not tightly couple application logic to a particular embedding implementation.
Conceptually:
                    RAG Platform
                         │
                Embedding Interface
                         │
             ┌───────────┴───────────┐
             │                       │
       Local Model              API Model


Similarly, vector storage should have a clean boundary:
                 Retrieval Layer
                        │
                  Vector Store
                        │
              ┌─────────┴─────────┐
              │                   │
        Local Vector DB      Other Backend

The initial implementation should remain minimal.
We should introduce abstractions only where they protect the rest of the system from implementation-specific decisions.

# 20. Alternatives Considered
## Keyword Search Only

Simple and inexpensive.
Rejected as the sole retrieval mechanism because lexical matching can miss semantically equivalent language.

Example:
vacation days
vs
annual leave entitlement
---

## Hosted Embedding API
Potentially strong quality and simple model management.
Not selected initially because the project prioritizes local, reproducible experimentation and minimizes external 
dependencies.

This remains a valid production alternative.
---

## Embedding Everything at Query Time
Rejected.
Document embeddings should be generated during indexing and persisted.
Only the incoming query needs to be embedded at query time.

---
## Mixing Different Embedding Models
Rejected.
Query and indexed documents need compatible representations.
Changing the embedding model generally requires re-indexing.

---
# 21. Key Trade-offs
| Decision                | Benefit                               | Trade-off                                              |
| ----------------------- | ------------------------------------- | ------------------------------------------------------ |
| Local embeddings        | Privacy, reproducibility, no API cost | Local compute required                                 |
| Dense vectors           | Strong semantic representation        | Higher storage/search cost than simple lexical methods |
| Batch embedding         | Better throughput                     | Higher memory usage                                    |
| Top-K retrieval         | Controls context size                 | Too low can hurt recall                                |
| Persistent vector store | Fast repeated retrieval               | Requires index lifecycle management                    |
| Model abstraction       | Provider/model flexibility            | Small additional abstraction                           |
| Separate experiments    | Faster learning and comparison        | Some duplication before integration                    |

# 22. Decisions for This Project
At the beginning of M4, the following are architectural intentions rather than final implementation choices:

1. Use an embedding abstraction in the platform.
2. Evaluate local open-source embedding models.
3. Evaluate embedding models using our actual HR/employee corpus.
4. Experiment with similarity metrics independently.
5. Experiment with normalization rather than assuming a strategy.
6. Evaluate Top-K retrieval behavior.
7. Evaluate local open-source vector stores independently.
8. Select the final embedding model based on quality and operational trade-offs.
9. Select the similarity strategy based on experimental evidence.
10. Select a local persistent vector store.
11. Integrate the selected components into the platform only after experimentation.
12. Keep the implementation minimal and avoid unnecessary framework abstractions.
