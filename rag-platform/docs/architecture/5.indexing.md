#### 2. What exactly is an index ?
An index is a persistent, searchable representation of the current document corpus, where each 
indexed unit is a document chunk containing its identity, content metadata, and embedding.

Index
│
├── Chunk A
│    ├── chunk_id
│    ├── document_id
│    ├── content
│    ├── metadata
│    └── embedding
│
├── Chunk B
│    ├── chunk_id
│    ├── document_id
│    ├── content
│    ├── metadata
│    └── embedding
│
└── Chunk C
     ├── chunk_id
     ├── document_id
     ├── content
     ├── metadata
     └── embedding

The vector store is therefore the persistence/query mechanism for the index, not the index lifecycle itself.

#### 3. What is our indexing unit?
Decision: DocumentChunk, Not the entire document.
Each chunk receives its own embedding. Why?
Because retrieval operates at chunk granularity. If we embedded an entire 30-page employee handbook as one 
vector, a query such as: "How many days of parental leave are available in India?"
would have poor retrieval granularity.

Document
   ↓
Chunks
   ↓
Embeddings
   ↓
Index

#### 4. Document identity vs Chunk identity
We need two levels of identity.
Document Identity:
Example: document_id = ZCompanyLLC/policies/leave-policy.md

Chunk Identity: 
Example: chunk_id = <document_id>:<chunk_number>

Consider the below scenario, 
Version 1
chunk-001 → parental leave
chunk-002 → sick leave
chunk-003 → vacation
Now, is someone adds 500 words at the beginning. We might get.. 
Version 2
chunk-001 → new introduction
chunk-002 → parental leave
chunk-003 → sick leave
chunk-004 → vacation

Therefore, chunk-number based identity causes unnecessary churn.
Decision: Use a content-derived deterministic chunk ID.
Conceptually: chunk_id = SHA256(document_id + chunk_content)
This gives us same document + same chunk content = same chunk_id

Idempotency
Running indexing twice should not create duplicate chunks.

#### 5. Do we need a document version? Yes.
But we should keep the first implementation simple.
Each indexed chunk should carry enough metadata to determine:
    Which document?
    Which version/content?
    Which chunk?
    Which embedding?

For Example: 
    {
        "document_id": "...",
        "document_hash": "...",
        "chunk_id": "...",
        "chunk_index": 7,
        "embedding_model": "BAAI/bge-small-en-v1.5",
        "embedding_dimension": 384,
        "chunking_version": "v1"
    }

Note: We dont need to use all of these fields in the prototype. 

#### 6. Document hash
We should calculate a deterministic hash of the canonical parsed document content.

For example: document_hash = SHA256(canonical_document_content)
Then: document A, 
    hash = abc123
If the source doesn't change:
document A, hash = abc123
No need to re-index.
If it changes:
document A,
    hash = xyz789
we know the indexed representation is potentially stale.

#### 7. Idempotency
This is an absolute necessity for index. 
Suppose we run: python scripts/index_documents.py once:
88 chunks indexed

Run it again:
88 chunks indexed

We should not end up with: 176 chunks
The operation should be idempotent.

Desired behavior
First run:
    new = 88
    updated = 0
    skipped = 0

Second run:
    new = 0
    updated = 0
    skipped = 88

This is a very useful production property.

#### 8. What happens when a document changes?
Suppose: leave-policy.md changes.
We calculate:
old document hash ≠ new document hash

Therefore: REINDEX DOCUMENT

The safe lifecycle is:
old chunks
     ↓
delete old document chunks
     ↓
parse new document
     ↓
chunk
     ↓
embed
     ↓
upsert new chunks

For our prototype, I prefer this over trying to perform clever chunk-level diffs.
Why? Because chunk boundaries themselves may change.
Trying to calculate:
old chunk → new chunk
adds considerable complexity without much value for our current corpus.

#### 9. What happens when a document is deleted?
This is equally important.
Suppose: employee_007.md is removed from: data/raw/ZCompanyLLC

Its vectors must not remain in the index. Otherwise we get stale retrieval results.
Therefore the indexing strategy needs reconciliation semantics:

Source Corpus
      ↓
discover documents
      ↓
compare against indexed documents
      ↓
identify deleted documents
      ↓
delete their chunks

This gives us:
Source of truth
       ↓
   filesystem
       ↓
      Index

The filesystem corpus is the source of truth for our prototype.

#### 10. Full rebuild
We should support a clean rebuild.
Conceptually: python scripts/index_documents.py --rebuild. 
would mean:

DELETE INDEX
    ↓
READ CORPUS
    ↓
PARSE
    ↓
CHUNK
    ↓
EMBED
    ↓
INDEX

This becomes extremely useful when:
    changing embedding models
    changing chunking strategy
    changing metadata
    changing index configuration
    recovering from corruption

For example:
bge-small
   ↓
384 dimensions

later becomes:
bge-base
   ↓
768 dimensions

We shouldn't mix the two representations accidentally.

#### 11. Embedding model belongs to index identity
This is a subtle but important production consideration.

Imagine: Index A
    BAAI/bge-small-en-v1.5
    384 dimensions

and later: Index B
BAAI/bge-base-en-v1.5
768 dimensions

Those aren't merely two versions of the same vector representation.
They're effectively different indexes.

Therefore our index metadata should capture at least:
    embedding_model
    embedding_dimension

Later we can introduce an explicit:
    index_version
    or:
    index_id

But not yet unless we actually need it.

#### 12. Metadata design
Each vector record should retain enough information for retrieval to return useful context.

At minimum:
{
    document_id,
    chunk_id,
    chunk_index,
    source,
    document_hash
}

And potentially:
    document_type
    title
    department
    country
    employee_id

depending on what the parser already produces.
For our HR corpus, this becomes particularly valuable.

Example:
{
    "document_id": "employees/india/EMP001.md",
    "chunk_id": "...",
    "country": "India",
    "document_type": "employee_profile",
    "employee_id": "EMP001"
}

This will become useful later for metadata filtering and hybrid retrieval.

#### 13. What should actually be stored in Chroma?
A chunk record logically becomes:

Chroma
│
├── id
│     └── chunk_id
│
├── document
│     └── chunk text
│
├── embedding
│     └── vector[384]
│
└── metadata
      ├── document_id
      ├── document_hash
      ├── chunk_index
      ├── source
      ├── document_type
      └── ...

This is an excellent fit for our current prototype.

#### 14. Upsert vs Add
Decision: upsert
We should use: upsert()
rather than: add()
because our chunk IDs are deterministic.

Conceptually:
same chunk_id
      ↓
same record
      ↓
update/replace

rather than creating another record.

This directly supports idempotency.

#### 15. Indexing should be deterministic

Given:
    same source documents
    same parser
    same chunking configuration
    same embedding model

we should produce:
    same chunks
    same chunk IDs
    same embeddings

This is extremely valuable for reproducibility.
The pipeline should therefore avoid things like: uuid.uuid4() for chunk identity.

UUIDs would make every indexing run appear to contain new data.

#### 16. M5 indexing contract
At the architectural level, I would define the workflow as: index(corpus) with this lifecycle:
                  ┌─────────────────┐
                  │ Discover source │
                  │   documents     │
                  └────────┬────────┘
                           ↓
                  ┌─────────────────┐
                  │ Calculate hash   │
                  └────────┬────────┘
                           ↓
                  ┌─────────────────┐
                  │ Compare indexed │
                  │     state       │
                  └────────┬────────┘
                           ↓
              ┌────────────┼────────────┐
              ↓            ↓            ↓
           unchanged     changed       new
              │            │            │
            skip       re-index      index
                           │            │
                           └─────┬──────┘
                                 ↓
                           Parse → Chunk
                                 ↓
                              Embed
                                 ↓
                              Upsert
                                 ↓
                         Update index state

        Missing from source
                 ↓
          Delete old chunks

#### 18. Finally, the architectural decisions. 
| Decision                  | Choice                               |
| ------------------------- | ------------------------------------ |
| Indexing unit             | **Document chunk**                   |
| Document identity         | Deterministic source-based ID        |
| Chunk identity            | **Deterministic content-derived ID** |
| Document change detection | Content hash                         |
| Vector operation          | **Upsert**                           |
| Duplicate protection      | Deterministic IDs + upsert           |
| Unchanged document        | Skip                                 |
| Changed document          | Re-index                             |
| Deleted document          | Remove its chunks                    |
| Full rebuild              | Supported                            |
| Source of truth           | Filesystem corpus                    |
| Vector persistence        | ChromaDB                             |
| Embedding model           | `BAAI/bge-small-en-v1.5`             |
| Embedding dimension       | 384                                  |
| Chunk metadata            | Persisted with vectors               |
| Separate indexing DB      | **No — not yet**                     |
| Framework                 | **None**                             |
| LangChain/LlamaIndex      | **No**                               |
