## ADR-XXX: Centralized Application Logging

**Status: Accepted**
**Date: 2026-09-08**
**Decision Owners: RAG Platform**
**Scope: Python pipeline components and executable scripts**


### 1. Context

The RAG platform consists of multiple Python components and executable pipeline scripts, including:
    document ingestion
    document parsing
    chunking
    embedding
    retrieval
    evaluation
    future indexing and RAG pipeline operations

These components need to produce operational information such as:
    - pipeline execution started/completed
    - documents discovered
    - documents successfully processed
    - processing failures
    - artifact locations
    - processing counts
    - configuration information relevant to an execution
    - exceptions and stack traces

Initially, logging configuration could be implemented independently within each executable script. However, as the number of pipeline components grows, this creates several problems:

    - duplicated logging configuration
    - inconsistent log formats
    - inconsistent log levels
    - different console/file behavior between scripts
    - difficulty changing logging behavior globally
    - tighter coupling between business/pipeline logic and logging infrastructure

Logging is therefore treated as a cross-cutting infrastructure concern rather than 
something owned independently by each pipeline script.

### 2. Decision

The project will use a centralized logging configuration within the Python application 
package.

The logging configuration is exposed through: rag_platform.logging
with a shared configuration function: configure_logging(...)

Individual scripts and modules obtain/configure their logger through this shared 
mechanism rather than creating their own handlers and formatters.

For example:
from rag_platform.logging import configure_logging

logger = configure_logging(
    logger_name=__name__,
    log_file="logs/ingestion.log",
)

Application code then uses the logger: 

logger.info(
    "document_parsed",
    extra={
        "document_id": str(document.id),
        "path": relative_path,
        "format": parsed.format.value,
    },
)

Note: No pront statements will be used for oeprational or pipeline status output. 

As of today, the elow script implement logging.

ingest_documents.py ──┐
                      ├──> rag_platform.logging
chunk_documents.py ───┘
                              │
                     ┌────────┴────────┐
                     ▼                 ▼
                  console        logs/*.log

### 4. Logging Responsibilities

The responsibilities are intentionally separated.

Pipeline components are responsible for:
deciding which events are meaningful
providing relevant contextual information
selecting the appropriate log level
recording exceptions

Example:

logger.info(
    "document_chunked",
    extra={
        "document_id": str(document.id),
        "chunks": len(chunks),
    },
)
Central logging configuration is responsible for:
    handlers
    log destinations
    formatting
    log levels
    structured JSON serialization
    console formatting
    log file creation

This prevents individual scripts from having to know how logging is configured.

### 5. Structured Logging

The file-based logs use structured JSON records rather than free-form text.

For example:

{
  "timestamp": "2026-09-08T12:30:41",
  "level": "INFO",
  "event": "document_chunked",
  "document_id": "abc123",
  "path": "sweden/policies/leave_policy.md",
  "chunks": 8,
  "artifact_path": "data/processed/chunks/ZCompanyLLC/sweden/policies/leave_policy.jsonl"
}

Structured logs make the output easier to:
    search
    filter
    parse programmatically
    aggregate
    ship to external logging systems later

The important design principle is that the event name remains machine-readable while contextual information is represented as structured fields.

### 6. Logging Destinations

For the prototype, logging is emitted to two destinations:

                     Logger
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
          Console          Log File
              │                 │
              ▼                 ▼
        Human-readable      JSON
        development output  structured output
Console

Used for immediate developer feedback while running pipeline scripts.

Example:

INFO ingestion_started
INFO document_parsed
INFO parsed_artifact_written
INFO metadata_written
INFO ingestion_completed
File

Stored under:
logs/
├── ingestion.log
└── chunking.log

The file representation is structured JSON.

### 7. Logging Events

Pipeline components should log meaningful lifecycle events rather than every line of execution.

For ingestion, representative events include:

ingestion_started
document_parsed
parsed_artifact_written
metadata_written
document_processing_failed
ingestion_completed

For chunking:

chunking_started
document_chunked
document_chunking_failed
chunking_completed

This gives us an operational view of the pipeline without turning the logs into a dump of implementation details.

### 8. Error Handling

Failures are recorded using the logging framework's exception support.

For example:

try:
    ...
except Exception:
    logger.exception(
        "document_processing_failed",
        extra={
            "document_id": str(document.id),
        },
    )

logger.exception() is used inside exception handlers so that the structured log contains the exception information and traceback.

This is preferable to logging only:

document processing failed

because the operational log should provide enough information to diagnose the failure.

### 9. Alternatives Considered
#### Option 1 — Configure logging independently in every script

Example:

ingest_documents.py
    └── logging configuration

chunk_documents.py
    └── logging configuration

embed_documents.py
    └── logging configuration
Advantages
    simple for a single script
    no shared infrastructure required
Disadvantages
    duplicated code
    inconsistent configuration
    inconsistent formatting
    difficult to change globally
    encourages each script to develop its own logging conventions
**Decision: Rejected.**

This does not scale cleanly as pipeline components are added.

#### Option 2 — Centralized logging configuration
                 logging configuration
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
     ingestion        chunking        embedding
Advantages
    single configuration point
    consistent format
    consistent handlers
    reusable by all Python components
    easy to change logging behavior globally
    clean separation of concerns
Disadvantages
    introduces a small shared infrastructure module
    requires pipeline components to follow a common logging convention
**Decision: Accepted.**

This provides the appropriate level of structure without introducing a third-party observability dependency.

#### Option 3 — Third-party logging framework

Examples include more feature-rich logging libraries or structured logging packages.

Advantages
Potentially provides:
    richer structured logging
    advanced formatting
    additional sinks
    filtering
    contextual logging features
Disadvantages
    additional dependency
    unnecessary complexity for the current prototype
    standard Python logging already provides the required capabilities
**Decision: Deferred.**

The project will use Python's standard logging library for the prototype.

#### Option 4 — Full centralized observability platform

Examples include:
    ELK / Elastic Stack
    OpenSearch
    Loki
    Datadog
    CloudWatch
    similar managed logging/observability platforms

Advantages
    Production systems can gain:
    centralized log aggregation
    search
    dashboards
    alerting
    retention policies
    correlation across services
    operational monitoring
Disadvantages
    infrastructure overhead
    additional operational cost
    unnecessary for the local prototype
    premature before the RAG pipeline becomes a deployed service

**Decision: Deferred.**

The current structured logging design deliberately keeps the application output compatible with future log aggregation systems.

### 11. Consequences

**Positive consequences**

Consistency - All Python pipeline components use the same logging conventions.

Maintainability - Logging configuration is maintained in one location.

Separation of concerns - Pipeline code records events; logging infrastructure controls 
how those events are emitted.

Structured operational data - JSON logs provide machine-readable execution information.

Future portability - The structured application logs can later be routed to centralized 
logging infrastructure without redesigning every pipeline component.

Better debugging - Document IDs, paths, chunk counts, parser versions, and exception 
information can be associated with individual events.

**Negative consequences** 

Shared dependency - Pipeline scripts now depend on the project's logging module.

Convention required - Developers must follow the project's structured logging 
conventions rather than arbitrarily creating their own handlers or using print().

Slightly more initial structure - A centralized logging module is more structure than a 
one-file script requires.

For this project, that trade-off is intentional because the platform contains multiple 
pipeline stages.

### 12. What Is Deliberately Not Included

The following are not part of this decision:
    distributed tracing
    metrics collection
    OpenTelemetry
    log aggregation infrastructure
    alerting
    dashboards
    log retention policies
    production log shipping
    correlation IDs across distributed services

These can be evaluated when the platform evolves from a local prototype into a deployed service architecture.

### 14. Final Decision

Centralized structured logging is adopted as a cross-cutting infrastructure capability 
of the RAG platform.

Individual pipeline components will emit structured log events through the shared 
logging configuration, while logging handlers, formatting, and destinations remain 
centralized.

The prototype will use local console and JSON log files. Production-grade log 
aggregation and observability infrastructure will be evaluated separately when 
deployment architecture warrants it.
