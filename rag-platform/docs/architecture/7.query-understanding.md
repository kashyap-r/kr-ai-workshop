
## M7. Query Understanding.

Query understandig is the intelligencelayer between the API and retrieval.

### Where does it line up in the overall flow?

Client

M6 Query API
  ▼

### 1. What problem does it solve?
It should determine things such as:

    What is the user actually asking?
    What are the important entities/concepts?
    Are there filters or constraints?
    Is the query ambiguous?
    Does it require query expansion/reformulation?
    What retrieval representation(s) should be generated?
    Is conversation context required?
    Is the query suitable for retrieval at all?

This module transforms a user query into a structured retrieval intent, it should 
not performa the retrieval itself. 

Eventually, it about the Query intent classification and also routing. 

### 2. What steps should query understanding contain?

#### A. Query Normalization
Cleanup superficial variation without changing the meaning. 

"WFH policy?"
        ↓
"What is the company's work-from-home policy?"

Examples:

whitespace normalization
spelling normalization where safe
obvious abbreviations
punctuation
terminology normalization

This should be deterministic initially.

#### B. Intent Detection 
Determine the broad information need.
For our HR corpus:

"What is the maternity leave policy?"
        ↓
intent = policy_lookup

Potential intents:
    policy_lookup
    employee_lookup
    benefit_lookup
    employment_terms
    general_information

#### C. Entity / Constraint Extraction 
Extract information that can potentially become retrieval filters.

Example: "How much maternity leave do employees get in Germany?"
{
  "entities": {
    "leave_type": "maternity",
    "country": "Germany"
  }
}
Example: "What is Alice's notice period?"
{
  "entities": {
    "employee": "Alice",
    "employment_term": "notice_period"
  }
}

This becomes particularly important when we reach Hybrid Retrieval, because 
metadata filtering can complement semantic retrieval.

#### D. Query Rewriting 
Potentially produce a retrieval-friendly version.
Example:
User: "What about Germany?"
Context: "We were discussing maternity leave."
        ↓
Rewritten query:
"What is the maternity leave policy for employees in Germany?"

Note: 
1. We shoudl not automatically rewrite every query.
2. A good architecture should preserve original_query, rewritten_query and allow downstream 
retrieval to decide what to use.

#### E. Query Expansion
Generate alternative retrieval expressions when useful.
Example:
"What is the WFH policy?"
        ↓
[
  "work from home policy",
  "remote work policy",
  "working remotely",
  "hybrid work policy"
]

Important point to remember: 
Query Expansion can improve recall while simultaneously introducing noise.
So this should probably be optional rather than unconditional.

#### F. Query Classification / Routing Metadata
This is about prodcuing the necessary signals / objects / artefacts for downstream components.

### 5.  Rule-based vs LLM-based Query Understanding

Option 1 — Rule-based
query
 ↓
regex / dictionaries / deterministic parsing
 ↓
structured query

Advantages
    deterministic
    cheap
    fast
    testable
    no model dependency

Disadvantages
    poor with complex language
    difficult to scale
    brittle query rewriting
    limited conversational understanding

Option 2 — LLM-based
query
 ↓
LLM
 ↓
structured JSON

Advantages
    understands natural language
    strong rewriting
    entity extraction
    ambiguity handling
    query expansion

Disadvantages
    latency
    cost
    nondeterminism
    hallucinated entities
    requires validation
    introduces provider/model dependency

Option 3 — Hybrid
             query
               │
       ┌───────┴────────┐
       ▼                ▼
 deterministic       LLM
 analysis            analysis
       │                │
       └───────┬────────┘
               ▼
          validated result

### 6. Where should conversational context live?
This is a subtle issue. The platform eventually needs to support: 
User: "What is the maternity leave policy?"
Assistant:
...

User:
"What about Germany?"

The second query cannot be understood correctly from the string alone. We need the full 
conversational state built into the system. That is again a future development. 

At this point consider that into the design. 
For example: 
QueryContext(
    query="What about Germany?",
    conversation_context=...
)
At this point conversation_context=None

### 7. Important design principle: preserve the original query 
Because later we need to:
    debug retrieval failures
    evaluate rewriting
    compare retrieval against original vs rewritten query
    explain system behavior
    trace requests through logs
    evaluate whether M7 actually improved retrieval

#### 5. Query normalization
Potential deterministic operations:
    trim whitespace
    collapse repeated whitespace
    normalize obvious punctuation spacing
    preserve semantic content

We should not aggressively:
    stem words
    remove stop words
    lowercase everything
    correct arbitrary spelling
    replace terminology using an uncontrolled dictionary

Why?
    Because our embedding model already handles much of the linguistic variation.

#### 7. Intent

Let's keep the first taxonomy tiny.
class QueryIntent(str, Enum):
    POLICY_LOOKUP = "policy_lookup"
    EMPLOYEE_LOOKUP = "employee_lookup"
    EMPLOYMENT_TERMS = "employment_terms"
    BENEFIT_LOOKUP = "benefit_lookup"
    GENERAL_INFORMATION = "general_information"
    UNKNOWN = "unknown"

#### 8. Entities and filters
This distinction is useful.

Entity is about "What concepts are present?"
{
  "country": "Germany",
  "leave_type": "maternity"
}

Filter is about "What metadata constraint can retrieval potentially apply?"
{
  "country": "Germany"
}

#### 9. Rewriting
rewritten_query is optional.
For a standalone query: "What is Germany's maternity leave policy?"
we may have: rewritten_query = None, because rewriting adds no value.

For: "What about Germany?"
with context: Previous topic = maternity leave
we could eventually produce: "What is the maternity leave policy in Germany?"
This means downstream components can use:
query = (
    result.rewritten_query
    or result.normalized_query
)
without losing the original query.

#### 10. Expansion
Same principle.
expanded_queries = [] unless expansion is actually useful.

Later:
[
  "work from home policy",
  "remote work policy",
  "working remotely policy"
]

#### 11. Logging
Every M7 request should be traceable.

Conceptually:

    query_understanding.error

With structured fields such as:
    request_id
    original_query
    normalized_query
    intent
    entity_count
    filter_count
    rewritten
    expanded_query_count
    duration_ms

### Implementation 

We will go with the hybrid approach for implementation..
Use rules by default, and invoke the LLM only when the query exhibits characteristics where deterministic rules are insufficient.

                         User Query
                             │
                             ▼
                  ┌────────────────────┐
                  │ Rule-based analysis│
                  └─────────┬──────────┘
                            │
                  ┌─────────▼──────────┐
                  │ Is query simple &  │
                  │ confidently parsed?│
                  └──────┬───────┬──────┘
                         │ YES   │ NO
                         │       │
                         ▼       ▼
                    Rule Result  LLM
                                 │
                                 ▼
                           Structured Result

Rule-based is enough for:
"What is the maternity leave policy in Germany?"
"How many days of annual leave do employees get?"
"What is Alice's notice period?"
"What is the WFH policy?"

These have obvious:
    intent
    entities
    constraints
    retrieval terms

There is little reason to spend an LLM call.

LLM becomes useful for queries like:
1. Conversational / elliptical queries
"What about Germany?"
"And India?"
"How long is it?"
"Is that paid?"

These require context and/or semantic interpretation.

2. Complex natural language
"If someone working in Germany has a child, what leave options
are available to them and how do they compare with Sweden?"

Rules become increasingly brittle here.

3. Ambiguous queries
"How much leave can I take?"
"What are the benefits?"
"Can I work from home?"

The system may need semantic interpretation to determine what the user means.

4. Queries requiring decomposition
"Compare maternity leave and parental leave in Germany and Sweden."

Query
 ├── Germany + maternity
 ├── Germany + parental
 ├── Sweden + maternity
 └── Sweden + parental

 This is a good future LLM use case.
