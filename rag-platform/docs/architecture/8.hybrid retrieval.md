# M8 — Hybrid Retrieval

## Objective

Combine complementary dense and sparse retrieval strategies while preserving the existing `Retriever` contract used by `QueryService`.

## Architecture

```text
Query API
   |
QueryService
   |
M7 Query Understanding
   |
Retriever
   |
HybridRetriever
   |-------------------|
DenseRetriever   BM25Retriever
   |                   |
Chroma             BM25IndexStore
   |                   |
   |-------------|-----|
                 RRF
                  |
          RetrievalResult[]
```

## M8 components

- `DenseRetriever`: semantic retrieval through embeddings and ChromaDB.
- `BM25IndexStore`: canonical chunk corpus for sparse retrieval, persisted atomically as JSON.
- `BM25Retriever`: Okapi BM25 over the sparse index.
- `RRFFusion`: rank-based fusion; raw dense and BM25 scores are never added directly.
- `HybridRetriever`: orchestrates dense + sparse retrieval and fusion.
- `retrieval.evaluation`: dependency-free Recall@K, Precision@K and reciprocal-rank helpers.

## Sparse index lifecycle

The existing M5 `Indexer` optionally receives a sparse index. New documents are upserted, changed documents have their old chunk IDs deleted before replacement, and deleted documents remove their old chunk IDs. The sparse index is persisted after synchronization. `--rebuild` clears both vector and sparse indexes.

The sparse index uses the same `DocumentChunk.chunk_id` as the vector index. This gives hybrid retrieval a stable join key and avoids duplicate chunk representations.

## RRF

For a chunk `d`:

`RRF(d) = sum(1 / (k + rank_r(d)))`

The implementation defaults to `k=60`. Fusion operates on rank because dense similarity and BM25 scores have different scales and semantics.

## Candidate depth

The current hybrid implementation asks both retrievers for `top_k` candidates and returns `top_k` fused results. Candidate over-fetching can be introduced as a later tuning parameter once evaluation data is available.

## API

The FastAPI application now constructs `HybridRetriever` using the persisted BM25 index at `data/processed/vector_store/ZCompanyLLC/bm25_index.json`. The public `/query` response contract remains unchanged.

If the sparse index has not yet been built, the BM25 retriever is empty and hybrid retrieval naturally falls back to the dense result set through RRF. Run `scripts/5.0.index_documents.py` to build/synchronize it.

## Evaluation

Use a human-reviewed JSONL relevance set:

```json
{"query":"...", "relevant_chunk_ids":["chunk-id"]}
```

Then run:

```bash
uv run python scripts/8.8.evaluate_retrieval.py path/to/relevance.jsonl --top-k 5
```

Compare Dense, BM25 and Hybrid using Recall@K, Precision@K and MRR. The evaluation set must remain independent of the retrieval implementation.

## M8 / M9 boundary

M8 establishes multi-strategy candidate generation. Cross-encoder/LLM reranking remains a separate second-stage ranking capability and belongs in M9 so that retrieval and reranking can be evaluated independently.

## Production evolution

For larger corpora, the local JSON BM25 index is a prototype implementation. A production deployment can move both sparse and dense retrieval to OpenSearch/Elasticsearch or another search platform while retaining the application-level `Retriever` and fusion contracts.
