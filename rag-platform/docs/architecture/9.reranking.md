## 1. What is reranking?

Reranking is a second-stage ranking process that takes an initial set of retrieved documents/chunks and reorders them according to their relevance to the user's query.

The key idea is:
First retrieve broadly → then rank deeply.

For example, suppose the user asks:
"What is the company's policy for working from home?"
The M8 hybrid retriever might retrieve 20 candidate chunks:

Hybrid Retrieval
       │
       ▼
20 candidate chunks
       │
       ├── Chunk A
       ├── Chunk B
       ├── Chunk C
       ├── ...
       └── Chunk T

These are good candidates, but the ordering isn't necessarily optimal.

Reranking takes those 20 candidates and asks a more sophisticated question for each:

"How relevant is THIS particular chunk to THIS particular query?"


2. Why isn't retrieval enough?

This is the key question.

Our M8 hybrid retrieval combines:

Dense retrieval → semantic similarity
BM25 → keyword/lexical matching
RRF → combines their rankings

This is excellent for candidate generation.

But retrieval is intentionally optimized for:

"Don't miss potentially relevant documents."

It isn't necessarily optimized for:

"Put the most relevant document at exactly rank #1."

Those are different optimization goals.

Example

Imagine the query:

"How many months of maternity leave are employees in Germany entitled to?"

Hybrid retrieval could return:

Rank 1   Employee handbook — general leave policy
Rank 2   Germany employment policy
Rank 3   Employee profile — Germany
Rank 4   Sweden maternity policy
Rank 5   India maternity policy

All five may have reasonable lexical or semantic similarity.

But a reranker can examine the query and the actual candidate text together and determine that:

Germany employment policy
        ↑
   highly relevant

should move to the top.

3. Why does a cross-encoder help?

This is where M9 becomes particularly interesting.

Our M8 dense retrieval effectively does:

Query → Embedding ─────┐
                       │ similarity
Chunk → Embedding ────┘

The query and chunk are embedded independently.

That's what makes vector retrieval fast.

A cross-encoder instead processes them together:

┌──────────────────────────────────────┐
│ Query + Candidate Chunk              │
│                                      │
│ "What is the maternity leave policy  │
│  in Germany?"                        │
│                                      │
│ "Employees working in Germany are    │
│  entitled to..."                     │
└──────────────────────────────────────┘
                  │
                  ▼
            Cross Encoder
                  │
                  ▼
        Relevance Score = 0.94

It can therefore model much richer interactions between the query and document.

4. The fundamental trade-off

There is a catch.

Cross-encoders are much more expensive than vector similarity.

Suppose we have 1 million chunks.

Doing:

Query × 1,000,000 chunks

through a cross-encoder would be far too expensive/slow.

So we use a two-stage retrieval architecture:

                 1st Stage
              FAST / BROAD
                   │
                   ▼
           ┌───────────────┐
           │ Dense + BM25  │
           │     + RRF     │
           └───────┬───────┘
                   │
              Top 20–100
                   │
                   ▼
                 2nd Stage
              SLOW / DEEP
                   │
                   ▼
           ┌───────────────┐
           │ Cross Encoder │
           └───────┬───────┘
                   │
                 Top 5
                   │
                   ▼
             LLM / Answer

That's the core reason M9 belongs after M8.
