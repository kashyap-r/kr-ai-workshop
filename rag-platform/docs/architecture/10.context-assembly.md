## 10. What exactly is Context Assembly?

Given the ranked chunks returned by retrieval/reranking, how do we construct the context that will be sent to the LLM?

Retrieval gives us relevant pieces of information.

Context Assembly turns those pieces into a coherent, bounded, ordered context package.

For example, M9 might return:
1. Sweden parental leave policy      score=0.91
2. Global parental leave policy      score=0.87
3. Employee handbook                 score=0.76
4. Germany parental leave policy     score=0.71
5. Leave request procedure           score=0.68

M10 decides:

which chunks actually enter the prompt
how they are ordered
how much text from each chunk is included
how duplicates/overlaps are handled
how much context is allowed
what metadata accompanies each chunk
how the assembled context is represented
how we measure context size
what happens when context exceeds the budget

This becomes the boundary between retrieval infrastructure and generation infrastructure.

### Core responsibilities of Context Assembly 
1. Context Selection 
2. Deduplication 
This is particularly important with hybrid retrieval.
The same chunk can potentially appear through:
    Dense retrieval + BM25 retrieval + Reranking

M8 should ideally already normalize/deduplicate candidates, but M10 should not blindly assume upstream components are perfect.

We need a stable identity:
document_id + chunk_id
or whatever canonical identifiers already exist in the project.
3. Ordering
The question is whether to preserve the order you get from the re-ranking. 
4. Context Budget
The LLM has a finite Context Window. We need to define a (Configurable) budget.
Token Counting
Option A — Character approximation
estimated_tokens = len(text) / 4
Option B — Model tokenizer
Use the tokenizer corresponding to the generation model.
Option C — Provider-specific tokenizer
Different generation providers/models can have different tokenization.
5. Context Formatting 
The LLM shouldn't receive a random concatenation. We need a 
deterministic Format. 

6. Context Package
Rather than returning just a string, it is recommended to  return a structured object.

M10 decides what context the generator receives; it does not generate the answer.

5. Contracts
Context Chunk 
This is the representation of an individual chunk after selection for context.

Proposed model:
@dataclass(frozen=True)
class ContextChunk:
    document_id: str
    chunk_id: str
    text: str
    rank: int
    retrieval_score: float | None
    rerank_score: float | None
    metadata: dict[str, Any]
    token_count: int

Note: Why do we need to retain both retrieval score and rerank_Score?
Both have two different notions of relevance. So, we may need for debugging and evaluation. 

6. Why ContextChunk rather than reusing M9's model?
This is an important architectural boundary.
We could simply pass M9's RerankedResult directly to M11.

M9 Owns Relevance ranking and M10 contextual representation. Those are diffeent responsibilities 

Contract #2 — ContextPackage
This is the main M10 → M11/M12 contract.

@dataclass(frozen=True)
class ContextPackage:
    query: str
    chunks: tuple[ContextChunk, ...]
    context_text: str
    token_count: int

Why tuple rather than list?
Because the package is an output artifact.

Once assembled: ContextPackage should be treated as immutable.
This reduces accidental mutation between: M10 → M11 → M12

Contract #3 — ContextAssemblyConfig
Configuration should be explicit.

@dataclass(frozen=True)
class ContextAssemblyConfig:
    max_context_tokens: int = 4000

@dataclass(frozen=True)
class ContextAssemblyConfig:
    max_context_tokens: int = 4000
    deduplicate: bool = True

That's enough for the prototype.
Having a separate contract for this leaves room for controlled evolution. 

Contract #4 — TokenCounter
This should be an abstraction.

from typing import Protocol
class TokenCounter(Protocol):
    def count(self, text: str) -> int:
        ...

That's deliberately tiny.
The assembler shouldn't know whether token counting is implemented using:
tiktoken
HuggingFace tokenizer
model-specific tokenizer
approximation

Contract #5 — ContextAssembler
The primary interface can remain extremely small:

class ContextAssembler:
    def assemble(
        self,
        query: str,
        results: Sequence[RetrievalResult],
    ) -> ContextPackage:
        ...

Deduplication Contract
The identity of a context chunk should be:
(document_id, chunk_id)

Therefore:
key = (result.document_id, result.chunk_id)

If the same chunk appears twice:
result #1
document=A
chunk=12

result #2
document=A
chunk=12

only one enters the context.

What about two chunks from the same document?

They are not duplicates.
For example:

document=A, chunk=12
document=A, chunk=13

Both are retained. This matters because a policy may span several chunks.

Ordering Contract
M10 will initially preserve M9 ordering.

Context Budget Contract
The selection algorithm should be deterministic.

### Formatting Contract
For the prototype, use a deterministic human-readable format.

For example:

[Context 1]
Document: employee_handbook
Chunk: employee_handbook_014

Employees may work remotely subject to manager approval.

[Context 2]
Document: sweden_leave_policy
Chunk: sweden_leave_policy_003

Employees are entitled to parental leave...

Notice that we're deliberately including identifiers.

This makes the context:

debuggable
inspectable
citation-ready
easy to test

### Error handling contract

M10 should validate configuration.

For example:

max_context_tokens <= 0

should fail immediately.

Likewise, malformed context results should not silently produce corrupted context.

But we should distinguish:

Invalid configuration

Raise an error.

No retrieved results

Valid condition:

ContextPackage(
    chunks=(),
    context_text="",
    token_count=0
)

This is important because zero retrieval results is not necessarily a system error.
