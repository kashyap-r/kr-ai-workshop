## M6.0 Query API 

The objective is to establish a clean query-ewntry contract: 

User Query
    │
    ▼
┌─────────────────┐
│   Query API     │
│                 │
│ validate input  │
│ create request  │
│ invoke pipeline │
│ return response │
└────────┬────────┘
         │
         ▼
   Retrieval Layer
         │
         ▼
   Ranked Chunks

At this point, I want something like..

POST /query
{
    "query": "What is the company's work from home policy?"
}

and eventually:
{
  "query": "What is the company's work from home policy?",
  "results": [
    {
      "chunk_id": "...",
      "document_id": "...",
      "text": "...",
      "score": 0.84,
      "metadata": {}
    }
  ]
}
No LLM-generated asnwer yet. 

The plan 

### M6.1 — Query API Architecture
Define:

Query request
Query response
API boundary
retrieval interface
error model
metadata contract
configuration
logging


### M6.2 — Query Entry Point
Implement the simplest query flow:
API
 ↓
Query Service
 ↓
Retriever
 ↓
Index
 ↓
Ranked Results

### M6.3 — Retrieval Integration
Connect the API to what I've already built in M4/M5:
query
  ↓
embedding
  ↓
vector search
  ↓
top-K chunks

I will reuse existing embedding/indexing abstractions, not create parallel implementations.

### M6.4 — API Validation & Error Handling
Handle things such as:

    empty query
    whitespace-only query
    excessively large query
    invalid top_k
    unavailable index
    malformed request
    no results

### M6.5 — Observability
The query path should use the structured logging we already established.

At minimum:
    request_id
    query_id
    query
    top_k
    retrieval latency
    number of results

Note: Be careful about logging actual user queries in a production system because queries can contain sensitive information. 
For the prototype, I can make that configurable.

### M6.6 — Query API Tests

Validate:
    valid query
    empty query
    invalid top_k
    no results
    successful retrieval
    index unavailable
    response schema

### Target Architecture
Keep the implementation intentionally small to enhance with additional features/ functionality in later modules.

Client

  ▼
QueryService

  ▼
