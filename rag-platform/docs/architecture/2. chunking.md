## Chunking 

At this point, the approach is to build the first workig RAG path, then using this working system as the base line we will experiment. 

We have many a option for Chunking strategy 
 ├── fixed-size
 ├── recursive
 ├── semantic
 ├── sentence
 ├── parent-child
 ├── contextual
 └── ...

For now we choose the below architecture for chunking 
    Parsed Documents
        ↓
    Baseline Chunker
        ↓
    DocumentChunks
        ↓
    local persistence
        ↓
    Embedding
        ↓
    Vector/Search
        ↓
    Retrieval
        ↓
    RAG
        ↓
    ────────────────────
    Experimentation
        ↓
    compare chunking strategies

The Question here is 
    How do we split a parsed document into retrieval units without destroying meaning?

For now, we will avoid the sophisticated semantic chunking

### Decision #1: What chunking strategy?
For this corpus, Structure-aware recursive chunking with a token/character budget

The important part isn't the exact algorithm yet. The baseline should:
    preserve document boundaries
    respect Markdown headings/sections where possible
    avoid splitting sentences unnecessarily
    have a maximum chunk size
    have a small overlap
    retain enough provenance metadata to trace every chunk back to its document

Something conceptually like:
ParsedDocument
│
├── # Sweden Leave Policy
│
├── ## Annual Leave
│       ...
│
├── ## Maternity Leave
│       ...
│
└── ## Sick Leave
        ...

Becomes:
Chunk 0 → Annual Leave section
Chunk 1 → Maternity Leave section
Chunk 2 → Sick Leave section

That's a much better initial baseline for an HR/policy corpus than blindly doing: every 
500 characters.

### Decision #3: Storage of Chunks (locally)
For this prototype
data/
├── raw/
│   └── ZCompanyLLC/
│
└── processed/
    ├── parsed/
    │   └── ZCompanyLLC/
    │
    └── chunks/
        └── ZCompanyLLC/

#### How is this different from parsed artifact? 
For parsed artifact:
    .txt → actual parsed text
    JSONL → central metadata registry

For Chunked arctifact: 
We'll use JSONL directly.
Because each chunk has both: chunk text + chunk metadata

The existing DocumentChunk already represents exactly that. It contains the chunk ID, 
document ID/version, chunking version, text, metadata, sequence number and offsets.

For Ex. 
        {
        "chunk_id": "...",
        "document_id": "...",
        "document_version": 1,
        "chunking_version": "baseline-v1",
        "text": "Employees are entitled to...",
        "metadata": {
            "path": "sweden/policies/leave_policy.md",
            "filename": "leave_policy.md"
        },
        "sequence_number": 3,
        "start_offset": 1240,
        "end_offset": 1872
        }
This is useful for experimentation. 

### ADR - Evaluate storage infrastructure options 
#### Option 1 - Local JSONL
Pros
    zero infrastructure
    transparent
    easy to inspect
    reproducible
    excellent for experiments
Cons
    no efficient querying
    poor concurrent access
    doesn't scale
    no vector search

#### Option 2 — Relational DB
Example: PostgreSQL (pgvector) 
Pros
    metadata filtering
    transactions
    operational maturity
    vector search possible
    one system for metadata + vectors
Cons
    operational overhead
    scale characteristics differ from specialized vector/search systems

#### Option 3 - Vector Database 
Example
    Qdrant, Milvus, WEaviate, Pinecone

Pros
    purpose-built vector retrieval
    filtering
    ANN indexes
    scalable retrieval
Cons
    additional infrastructure
    operational complexity
    vendor/system-specific concerns

#### Option 4 — Search engine
For example:
    Elasticsearch / OpenSearch

This becomes particularly interesting when we eventually want:

    BM25
    +
    dense vectors
    +
    metadata filtering
    +
    hybrid retrieval

which fits our eventual retrieval architecture very well.
