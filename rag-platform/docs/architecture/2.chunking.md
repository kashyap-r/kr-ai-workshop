# M3 — Chunking: Design Decisions and Strategy

## 1. Context

Chunking transforms a parsed document into smaller retrieval units that can be embedded, indexed and retrieved independently.

The initial M3 implementation introduced a deterministic fixed-character-window chunker with configurable chunk size and overlap.

The initial implementation established:
- A `Chunker` domain contract.
- A `RecursiveChunker` implementation.
- Deterministic chunk identifiers.
- Chunk sequence numbers and character offsets.
- Chunking version lineage.
- Unit tests for size, overlap, determinism, validation and offsets.

The initial implementation is a baseline. It does not yet implement true recursive or structure-aware splitting.

This design review establishes the target chunking strategy before further implementation changes.

## 2. Problem Statement

Arbitrary character-window splitting can divide meaningful content across chunk boundaries.

Potential consequences include:
- Sentences being split.
- Paragraphs losing their context.
- Headings becoming detached from their content.
- Lists and tables being fragmented.
- Important policy rules and exceptions being separated.
- Incomplete evidence being retrieved and passed to the generator.

Chunking must balance retrieval granularity, semantic completeness, model token limits, indexing cost and downstream context requirements.

## 3. Chunking Strategy Options

### 3.1 Character-based chunking

Splits documents using a fixed number of characters, optionally with overlap.

Advantages:
- Simple implementation.
- Low computational overhead.
- Deterministic.
- No tokenizer dependency.

Limitations:
- Does not understand document structure.
- Can split sentences, paragraphs and lists.
- Character counts do not reliably predict model token counts.

Decision: Retain as a baseline for comparison, not as the preferred production strategy.

### 3.2 Token-based chunking

Splits documents using a tokenizer and a configured token budget.

Advantages:
- Better control over embedding model input limits.
- Predictable token budgets.
- Better context-window management.

Limitations:
- Requires tokenizer integration.
- Does not inherently preserve semantic or structural boundaries.
- Tokenization can differ across models and tokenizer versions.

Decision: Use tokenization for chunk-size enforcement, not as the sole boundary-selection strategy.

### 3.3 Structure-aware chunking

Uses document structure to determine meaningful boundaries.

Structures include:
- Headings and subheadings.
- Paragraphs.
- Lists.
- Tables.
- Sections and subsections.

Advantages:
- Preserves logical document organization.
- Keeps related content together.
- Improves evidence completeness.
- Particularly appropriate for enterprise policies, handbooks and technical documentation.

Limitations:
- Requires format-specific structural extraction.
- Complex PDFs and tables need additional handling.
- Large structural units still require splitting.

Decision: Adopt as the primary chunk-boundary strategy.

### 3.4 Semantic chunking

Uses semantic similarity, sentence embeddings or topic-shift detection to identify boundaries.

Advantages:
- Can identify topic transitions in unstructured content.
- Useful when document structure is absent or inconsistent.

Limitations:
- Additional computational cost.
- Requires embedding calculations and threshold tuning.
- Semantic similarity does not guarantee logical completeness.
- Chunk sizes can vary.

Decision: Defer as an advanced alternative. Evaluate only if structure-aware chunking proves insufficient.

## 4. Key Design Decision

Adopt a hybrid **structure-aware, token-bounded chunking strategy with controlled overlap**.

The design separates two concerns:

1. Boundary selection: determine where content should be split using document structure and sentence boundaries.
2. Size enforcement: use tokenization to ensure chunks remain within the embedding model's input budget.

The strategy should:

1. Preserve headings with their associated content.
2. Prefer complete paragraphs and list groups.
3. Split oversized sections at paragraph boundaries.
4. Split oversized paragraphs at sentence boundaries.
5. Use whitespace boundaries as a final fallback.
6. Enforce a configurable token budget.
7. Apply overlap only when necessary to preserve continuity.
8. Preserve document identity, version, source metadata and chunk lineage.

## 5. Initial Configuration Hypothesis

Initial experimental configuration:

- Target chunk size: 500 tokens.
- Maximum chunk size: approximately 700 tokens.
- Overlap: up to 10% of target size, where necessary.

These are starting values, not universal optimal values.

Final settings will be determined through retrieval and downstream answer-quality evaluation.

## 6. Chunk Size and Overlap Considerations

Smaller chunks:
- Provide finer retrieval granularity.
- Can improve precision.
- Increase the number of indexed chunks.
- Risk losing surrounding context.

Larger chunks:
- Preserve more context.
- Reduce the number of indexed chunks.
- Can introduce irrelevant content into retrieval results.
- Consume more downstream context tokens.

Overlap:
- Helps preserve continuity across split boundaries.
- Increases indexed content and embedding workload.
- Can cause duplicate retrieval results.
- Must not be used as a substitute for appropriate structural boundaries.

The system should support configurable overlap, including zero overlap.

## 7. Metadata and Lineage

Each generated chunk must retain:

- Document ID.
- Document version.
- Chunking version.
- Sequence number.
- Start and end offsets.
- Source/document metadata.

The chunking configuration and tokenizer identity/version should be recorded as part of processing lineage so that chunks and indexes can be reproduced.

Document version propagation from the parsed document into the chunker remains an explicit domain-model issue to resolve before indexing.

## 8. Evaluation Plan

Compare four approaches using the same source corpus:

- C1: Character-based.
- C2: Token-based.
- C3: Structure-aware and token-bounded.
- C4: Semantic and token-bounded.

Evaluate:

### Chunk quality
- Structural completeness.
- Sentence and paragraph fragmentation.
- Chunk-size distribution.
- Oversized chunks.
- Duplication caused by overlap.

### Retrieval quality
- Recall@K.
- Precision@K.
- Hit Rate@K.
- MRR.

### Answer quality
- Answer correctness.
- Groundedness.
- Citation accuracy.
- Completeness.

### Operational characteristics
- Chunking execution time.
- Number of generated chunks.
- Embedding token volume.
- Index storage.
- Query-time context size.

Keep the corpus, embedding model, retrieval configuration and evaluation queries constant when comparing chunking strategies.

## 9. Alternatives Considered

| Strategy | Decision |
|---|---|
| Fixed character windows | Baseline only |
| Fixed token windows | Size enforcement baseline |
| Structure-aware only | Insufficient token-budget control |
| Semantic only | Deferred due to cost and complexity |
| Structure-aware + token limit | Selected |
| Structure-aware + token limit + controlled overlap | Preferred implementation |

## 10. Deferred Implementation Work

The following work is not yet completed:

- Replace arbitrary fixed-window splitting with structural boundary selection.
- Add tokenizer integration and token-budget enforcement.
- Implement paragraph and sentence fallback splitting.
- Refine overlap handling.
- Resolve document-version propagation.
- Record tokenizer and chunking configuration lineage.
- Add representative PDF, Markdown and TXT fixtures.
- Benchmark chunking strategies using the Golden Dataset.

## 11. Final Decision

The project will use structure-aware chunking with token-budget enforcement and controlled overlap as its primary strategy.

Character-based and token-only approaches remain experimental baselines. Semantic chunking remains a future optimization for content where structural boundaries are insufficient.

Implementation changes will follow this documented design decision.
