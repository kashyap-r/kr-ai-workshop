LOGGING 


In this RAG platform, I have treated logging as a cross-cutting infrastructure concern rather than implementing logging independently in each pipeline component.

I introduced a centralized logging configuration using Python's standard logging framework.

The idea was to separate the responsibility of generating operational events from the responsibility of configuring how those events are handled.

Individual components such as ingestion and chunking obtain their loggers through the shared configuration. We use separate log files for different pipeline stages, while maintaining a consistent logging format.

We have two output handlers: a console handler for immediate developer feedback and a file handler that produces structured JSON logs.

We log meaningful lifecycle events, processing statistics, artifact locations and exceptions with contextual information such as document IDs and source paths.

This makes troubleshooting easier, provides visibility into pipeline execution and gives us a consistent foundation for extending the platform.

For the prototype, we deliberately stayed with Python's standard logging library and local files. In production, these structured logs could be forwarded to CloudWatch, OpenSearch, Datadog or another centralized logging platform.

Concept	                What it means
Logger	                Produces log events
Log level	            INFO, DEBUG, WARNING, ERROR, CRITICAL
Handler         	    Determines where logs are sent
Formatter	            Determines how logs are represented
Structured logging	    Logs represented as machine-readable fields
Contextual logging	    Adds information such as document ID, tenant ID, execution ID
Exception logging	    Captures exception details and stack traces

Difference between Logging and Monitoring 
    Loggin records individual events. Monitoring tracks system health through metrics, thresholds, and alerts. The complement each other. 

Difference between Logging and Distributed Tracing

Logging records evets, while distributed tracing follows a request across multiple services and captures its execution path and timing. 

How to scale this logging architecture in Production ?
Emit structured logs to stdout or a collector, forward thm through an agent or elemetry pipeline, aggregate them in a platform such as cloudwatch or opensearch, and add retention, access controls, dashboards and alerting. 

How is logging different to Observability ?

- Logging tells you what happened 
- Monitoring tells you whether soemthing is healthy 
- Observability helps you undertand why something is happening, including problems you didnt ancticipate.

Observability is broader than logging. Logging is one of its key components, but it is not observability by itself.

2. The three pillars of observability
In conventional software and distributed systems, observability is commonly built around three pillars:
1. Logs
2. Metrics
3. Traces

Let's understand each in detail.
A. Logs — individual events
Logs are timestamped records of things that happened inside an application.

In our ingestion pipeline, we already have events such as:
{
  "timestamp": "2026-11-08T10:30:00",
  "level": "INFO",
  "event": "document_parsed",
  "document_id": "abc123",
  "format": "pdf",
  "characters": 12500
}

Logs answer questions such as:
- Which document failed?
- Which parser was used?
- What exception occurred?
- Which tenant was processing the document?
- When did the failure happen?
Characteristics:
- Event-oriented.
- Often high-cardinality contextual information.
- Useful for debugging and auditing.
- Can be structured or unstructured.
- Can contain application-specific business context.
Our centralized logging implementation addresses this pillar.

B. Metrics — numerical measurements over time
Metrics are numerical measurements collected at regular intervals or when events occur.

Unlike logs, metrics are aggregated and are particularly useful for identifying trends, bottlenecks and anomalies.

For our RAG platform, consider these examples:
Component	Metric	                        Example
Ingestion	Documents processed/min	        120
Parsing	    Average parsing time	        450 ms
Chunking	Chunks generated/document	    12
Embeddings	Embedding throughput	        80/sec
Retrieval	p95 latency	                    650 ms
Reranking	Average reranking time	        120 ms
Generation	Tokens/sec	                    45
API	Error rate	                            2.5%

Metrics help answer:
- Is ingestion slowing down?
- Is embedding throughput decreasing?
- Is retrieval latency increasing?
- Are API errors increasing?
- Is GPU memory approaching capacity?
Important metric concepts
You should understand these four terms for interviews:
Term	Meaning
Counter	Cumulative count, e.g. total failed requests
Gauge	Current value, e.g. GPU memory usage
Histogram	Distribution of observations, e.g. request latency
Summary	Statistical observations, depending on the metrics system

For example, a latency histogram allows us to calculate:
- p50 — median latency
- p90 — 90% of requests complete within this time
- p95 — 95% complete within this time
- p99 — 99% complete within this time
Why are percentiles important?
Suppose 1,000 API requests have these characteristics:
- Average latency: 400 ms
- p50: 250 ms
- p95: 1.8 seconds
- p99: 4 seconds
The average alone hides the experience of the slowest requests.

This is why production systems pay particular attention to p95 and p99.

3. How logs, metrics and traces work together
The real value comes when you correlate all three.

Imagine a user reports:
My question took unusually long to answer, and the answer wasn't relevant.

Here's how we investigate.
Investigation	What we use	What we discover
Was the system slow?	Metrics	p95 latency increased
Which component was slow?	Traces	Retrieval took 1.5 seconds
Why was retrieval slow?	Logs	Vector search timed out and retried
Was answer quality affected?	Retrieval and generation diagnostics	Relevant chunks were not retrieved

This is observability in practice.

This is especially important when a request travels across several services.

Interview point: Logging without correlation becomes difficult to use in distributed systems. Correlation IDs connect events belonging to the same execution.
5. What does observability look like in our RAG platform?
This is where the topic becomes particularly relevant to your project.

Traditional application observability tells us whether the software is functioning correctly.

But a RAG system introduces another dimension: the quality of the AI pipeline itself.

A RAG application can be technically healthy and still produce terrible answers.

For example:
- API is responding successfully.
- No exceptions are being generated.
- Latency is within acceptable limits.
- Vector database is healthy.
- LLM is responding.
Yet the answer is factually incorrect because retrieval returned irrelevant chunks.

Traditional infrastructure monitoring might not detect that problem.

We need additional RAG-specific observability.
A. Pipeline-level observability
Consider each stage of our pipeline.
Pipeline stage	What should we observe?
Ingestion	Documents discovered, processed, failed
Parsing	Parsing duration, failures, output size
Chunking	Chunks/document, chunk size distribution
Embeddings	Embedding latency, throughput, model failures
Indexing	Indexing duration, indexed document/chunk count
Query understanding	Query classification, rewriting, routing
Retrieval	Candidate count, relevance scores, latency
Reranking	Reranking latency, score distribution, rank changes
Context assembly	Context size, token count, truncation
Generation	Model latency, token usage, failures
Citations	Citation coverage, citation validation failures

For example, suppose retrieval returns 20 candidates, but reranking pushes the genuinely relevant document from rank 2 to rank 18.

We should be able to investigate that.

This requires more than an API error log.
B. AI quality observability
There is another layer beyond infrastructure and pipeline performance.

We need to understand whether the RAG system is actually answering questions correctly.

Some useful measurements are:
Metric	What it tells us
Context precision	How much retrieved context is relevant
Context recall	Whether the relevant information was retrieved
Faithfulness	Whether the answer is supported by retrieved context
Answer relevance	Whether the answer addresses the question
Citation correctness	Whether citations support the associated claims
Retrieval hit rate	Whether expected relevant documents appear in retrieved results

These are quality measurements, not ordinary infrastructure metrics.

For example:

Question: What is the maternity leave policy for an employee based in India?

The system retrieves a Swedish maternity leave policy instead of the Indian policy.

From an infrastructure perspective:

Healthy
 API returned HTTP 200.

From an observability and quality perspective:

Problem
 Retrieval selected the wrong country policy.

This distinction is extremely important in production AI systems.
