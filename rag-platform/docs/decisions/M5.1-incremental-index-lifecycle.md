#### 2. Introduce an index manifest
For this prototype, I recommend a small JSONL/JSON manifest on disk, rather than introducing PostgreSQL or another database.

data/

    └── vector_store/
        └── ZCompanyLLC/

 #### 5. Changed document lifecycle

Suppose: employee_001.md
has:  
old hash = ABC
new hash = XYZ

We don't attempt a sophisticated chunk diff.
Instead..

OLD CHUNKS
    ↓
DELETE
    ↓
RE-CHUNK
    ↓
EMBED
    ↓
UPSERT
    ↓
UPDATE MANIFEST

#### 6. Deleted documents

This is where the manifest becomes particularly valuable.
Suppose the manifest contains:
A
B
C
D

but the current corpus contains:
A
B
D

Then: C has disappeared.
Therefore:

document C
    ↓
delete all chunk_ids belonging to C
    ↓
remove C from manifest

This prevents stale information from remaining searchable.

#### 7. We need one VectorStore capability

There's an important consequence.
Our current VectorStore protocol supports:
    upsert()
    query()
but not deletion.
Therefore I now have to extend it with something like:

def delete(
    self,
    ids: Sequence[str],
) -> None:
    ...

And Chroma can implement that using its existing collection.
This is a legitimate evolution of the abstraction because index lifecycle now requires deletion.

#### 8. Don't add delete_document() to VectorStore

Because Vector Store fundamentally stores chinks,not documents.
Instead, the indexing layer knows document -> Chunk IDs and the Vector store knows Chunk ID -> Vector Record 

#### 8. Manifest Ownership:
The manifest belongs to the indexing layer. So, the script should be located accordingly.
