## Preliminary Embedding Model Selection

### Selected model

`BAAI/bge-small-en-v1.5`

### Rationale

The three candidate models were evaluated using the existing ZCompanyLLC
`DocumentChunk` corpus and six experiment-specific HR queries.

All three models demonstrated basic semantic retrieval capability.

`BAAI/bge-small-en-v1.5` was selected for the next stage because it provided
strong retrieval behavior while maintaining a substantially lower operational
cost than `BAAI/bge-base-en-v1.5`.

Key observations:

- 384-dimensional embeddings
- float32 vectors
- normalized embeddings
- approximately 871 chunks/sec on the experiment workload
- correctly retrieved answer-bearing HR policy content for the leave-request
  query, where MiniLM retrieved a leave record instead
- correctly retrieved the India WFH policy for the India-specific query
- broadly comparable semantic behavior to BGE-base on the experiment probes

`BAAI/bge-base-en-v1.5` showed strong retrieval behavior and occasionally
produced preferable rankings, but its 768-dimensional vectors and substantially
higher embedding cost were not justified by a sufficiently consistent quality
improvement in this small experiment.

`sentence-transformers/all-MiniLM-L6-v2` remains a useful lightweight baseline
but was not selected for the next stage because the experiment exposed weaker
semantic specificity on some HR queries.

### Important qualification

This is a preliminary engineering decision based on a small experiment-specific
query set. It is not the formal retrieval evaluation or Golden Dataset.

The selected model will be re-evaluated during next stage of experimentation when similarity metrics,
Top-K behavior, and retrieval evaluation are studied more systematically.

For details on this experiments and their results, please refer to the below notebook 
/experiments/similarity_and_retrieval_expt.ipynb

## Conclusions

- BGE-small produces normalized embeddings, making cosine similarity and
  dot product effectively equivalent for the current model configuration.
- Similarity scores provide a ranking signal but should not be interpreted
  using a universal relevance threshold.
- Increasing Top-K increases context coverage but also introduces less
  relevant chunks.
- Small changes in a similarity threshold can produce large changes in the
  number of retrieved chunks.
- For the prototype, retrieval will use fixed Top-K selection.
- A configurable score threshold may be introduced later after proper
  retrieval evaluation.
  
**- The initial prototype retrieval configuration is Top-K = 5 with no similarity threshold.**
