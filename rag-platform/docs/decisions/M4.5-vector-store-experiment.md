Vector Store Experiment

## Objective
Evaluate a local persistent vector store for the RAG prototype.

The experiment will verify:
- storing BGE-small embeddings
- storing chunk identity and metadata
- similarity search
- Top-K retrieval
- local persistence
- reopening the store across executions

The experiment uses the existing M3 `DocumentChunk` representation and the selected embedding model.
No production vector-store abstraction is introduced yet.

Conclusion

ChromaDB 1.5.9 is selected as the prototype vector store.

The experiment verified:

- 88 BGE-small embeddings can be stored successfully.
- Chunk text and metadata can be stored alongside vectors.
- Similarity search returns the expected ranking.
- The persisted collection can be reopened successfully.
- Chroma's reported distance preserves the same ranking as our cosine
  similarity calculation.

For the prototype, ChromaDB provides sufficient local persistence and
vector-search capability without introducing an external database service.

Platform Vector Store Implementation

### Implementation

The platform introduces a `VectorStore` protocol as the infrastructure boundary for vector persistence and similarity search.

The prototype implementation is `ChromaVectorStore`, backed by ChromaDB's persistent local storage.

The boundary is:

EmbeddingModel
      │
      ▼
VectorStore
      │
      ▼
ChromaVectorStore

The vector store accepts DocumentChunk objects and their corresponding embeddings. It persists:

chunk ID
embedding vector
chunk text
retrieval metadata

The DocumentChunk model itself does not contain an embedding.

Why keep embeddings outside DocumentChunk?

Embeddings are derived artifacts produced by a particular embedding model and configuration. Keeping them separate avoids coupling the domain model to a specific embedding representation or provider.

This also allows the same chunk to potentially have embeddings generated by different models or versions without changing the core document/chunk representation.

Vector Store Contract
The prototype contract intentionally exposes only two operations:

upsert() — store or update chunk embeddings
query() — retrieve the most similar chunks

Additional capabilities such as deletion, metadata filtering, namespaces, hybrid retrieval, and advanced indexing are deferred until required.

Chroma Adapter

ChromaVectorStore translates between the platform's VectorStore contract and ChromaDB's API.

Chroma returns a distance value. The adapter converts this to the platform-level similarity score used by RetrievalResult.

For the normalized BGE-small embeddings used by the prototype: Chroma distance = 2 × (1 - cosine similarity)
Therefore: similarity = 1 - (distance / 2)

Validation

The implementation was validated against the vector-store experiment using the ZCompanyLLC HR corpus:

88 chunks indexed
BGE-small embeddings
384-dimensional vectors
persistent ChromaDB collection
query-side retrieval successfully reproduced the experiment results
Top-5 ranking and similarity scores matched the experiment

Example query:

How many days can an employee based in India work remotely each week?

The implementation returned the India WFH Policy as rank 1 with a similarity score of approximately 0.8432, matching the vector-store experiment.

Architectural Decision
Decision: Use a small VectorStore protocol with a ChromaDB adapter.

Rationale:

preserves infrastructure boundaries
keeps the domain model independent of vector storage
allows the vector-store implementation to change later
provides a simple retrieval contract
avoids introducing a framework-specific dependency into the rest of the platform

Trade-off: The abstraction currently exposes only basic vector operations and does not capture more advanced capabilities offered by specific vector databases. Those capabilities will be introduced only when required by later retrieval needs.
