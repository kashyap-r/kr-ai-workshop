The most important design principle:
Dense retrieval and sparse retrieval are independent retrieval strategies. Hybrid retrieval 
orchestrates them.

#### 2. M8.1 Architecture
I'd introduce four conceptual contracts.
A. Retriever
The common interface for any retrieval strategy.
class Retriever(Protocol):
    def retrieve(
        self,
        query: str,
        top_k: int,
    ) -> list[RetrievalResult]:
        ...

Both the DenseRetriever and SparseRetriever will implement it. 

B. Retreieval Result
@dataclass(frozen=True)
class RetrievalResult:
    chunk_id: str
    score: float
    rank: int
    metadata: dict[str, Any]

Note: A dense score and a BM25 score are not directly comparable.
The initial fusion mechanism should operate on rank, not raw scores.
That's why RRF is a good first implementation.

#### 3. RRF — Reciprocal Rank Fusion

For each result:

RRF(d)=sum_{r in R} * ( 1 / (k + rank_r(d))

Where:
d = document/chunk
R = retrieval systems
rank_r(d) = rank assigned by retriever r
k = smoothing constant, commonly 60

Example: 
Dense:
A → rank 1
B → rank 2
C → rank 3
BM25:
B → rank 1
D → rank 2
A → rank 3

RRF: 
A = 1/(60+1) + 1/(60+3)
B = 1/(60+2) + 1/(60+1)
C = 1/(60+3)
D = 1/(60+2)

B gets a strong hybrid score because both retrieval systems independently found it.

This module will implement the below packages / objects:
base.py -    Retriever contract
models.py - RetrievalResult
dense.py - Existing DenseRetriever
sparse.py - BM25Retriever
fusion.py - RFFusion
hybrid.py - HybridRetriever

#### 6. Sparse retrieval choice
For this prototype, I'd go with BM25.
Why? Because it demonstrates a fundamental weakness of dense retrieval.

Consider a query:
What is the employee ID for EMP-1042?
Dense retrieval may understand the semantic concept.

BM25 is naturally good at:
EMP-1042
PIP
S3
AWS
Germany
2025

#### 7. Where should the BM25 index live?
For M8, keep it simple:
parsed/chunks
       │
       ├──────────────► Vector index
       │
       └──────────────► BM25 index

I will build a local BM25 index from the same canonical chunk collection.

Potential implementation:
rank_bm25 or a lightweight custom implementation if we want to demonstrate the algorithm.

I'd initially use a well-tested BM25 implementation rather than spending M8 building tokenization and BM25 mathematics ourselves.

The architecture matters more than reinventing the library.

#### 8. Critical issue: canonical chunk identity
Hybrid retrieval requires both retrievers to refer to the same chunks.

Therefore:
Dense result
chunk_id = abc123

BM25 result
chunk_id = abc123

must resolve to the same underlying chunk.
This means chunk_id becomes extremely important.
Verify the existing M5 index has a stable identifier.

9. Score semantics

We should explicitly document three different concepts:

Retrieval score

Produced by an individual retriever.

Dense → cosine similarity
BM25  → BM25 score
Rank

Position within that retriever's result set.

1, 2, 3, ...
Fusion score

Produced by RRF.

RRF score

These should not be conflated.

A result could therefore look conceptually like:

{
  "chunk_id": "chunk-123",
  "score": 0.0325,
  "rank": 1,
  "retriever": "hybrid"
}

Internally we may retain:

dense_score
sparse_score
dense_rank
sparse_rank
fusion_score

That will be extremely useful for debugging and evaluation.

10. Configuration

Don't hard-code:

dense_top_k = 10
sparse_top_k = 10
final_top_k = 5
rrf_k = 60

Instead, define configuration.

For example:

@dataclass(frozen=True)
class HybridRetrievalConfig:
    dense_top_k: int = 20
    sparse_top_k: int = 20
    final_top_k: int = 10
    rrf_k: int = 60

Why retrieve 20 from each if we ultimately need 10?

Because:

Top 10 dense
+
Top 10 sparse

can miss useful documents that rank 11–20 in one system but rank very highly in the other.

A larger candidate pool gives fusion more opportunity.

We'll validate these numbers experimentally rather than treating them as universal defaults.

#### 9. Tokenization decision: 
Tokenization decision: The BM25 tokenizer preserves identifier-like tokens containing - and _, while applying case folding. This is intended to improve lexical retrieval for employee IDs, policy identifiers, acronyms and other domain-specific terms.

#### 10. BM25IndexStore

This is not yet BM25 scoring.

Think of it as the sparse equivalent of your vector index's storage layer.

DocumentChunk[]
       │
       ▼
BM25IndexStore
       │
       ├── chunk_id → DocumentChunk
       │
       └── persistence

The internatl structure: 
chunk_id
   ↓
DocumentChunk

That's important because both dense and sparse retrieval ultimately need to return the same canonical DocumentChunk.

Documentation point 📝

Capture:

BM25 statistics are lazily rebuilt based on an index revision rather than recalculated on every query.

And the trade-off:

Recalculate every query
    → simple
    → expensive

Eager rebuild after every mutation
    → current
    → potentially wasteful

Revision-based lazy rebuild
    → efficient for repeated queries
    → first query after mutation pays rebuild cost

This is exactly the sort of engineering trade-off you wanted captured.

The important separation is:
    Dense/BM25 = candidate generation
    RRF = candidate fusion
    M9 = candidate reranking

2. Why RRF?
Dense and BM25 produce scores on completely different scales:
Dense       ~0.0–1.0
BM25        ~0–10+

The  actual query demonstrated this:
Dense:  0.756336
BM25:   9.410023

Comparing these raw numbers directly would be meaningless.

RRF instead uses rank:
RRF(d) = Σ 1 / (k + rank(d))
with:
k = 60

So we combine relative ordering, not incompatible score magnitudes.

3. Why retrieve more candidates?

Your HybridRetriever uses:

candidate_k = max(top_k, top_k * candidate_multiplier)

with the default multiplier of 4.

Therefore:

Requested top_k = 5
             ↓
Dense retrieves 20
BM25 retrieves 20
             ↓
RRF
             ↓
Return top 5

This gives each retrieval strategy a larger candidate pool before fusion.

That's particularly important once we reach M9, because the reranker needs a reasonable candidate set to work with.

4. Failure behavior

The implementation also explicitly handles:

Dense empty + Sparse available
        ↓
return sparse

Sparse empty + Dense available
        ↓
return dense

Both empty
        ↓
empty result

That was actually exposed during our validation when the persistent BM25 index was missing.

The hybrid pipeline didn't crash—it fell back to dense retrieval.
